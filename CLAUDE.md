## 1. Project Overview

This project is a single landing page for **After Hours**, a leather-goods collection by Fableroom, handmade at a workshop in India (Hosting & Bar, Furniture, Leather Accessories categories, unified by six textures: Croco, Split suede, Hair-on-hide, Plain, Fine-grained, Shagreen). **"Three Sixty" — the workshop's actual name — is used in this file for internal context only and must NEVER appear anywhere on the live page.** It was removed from every mention on the page (title tag, meta description, promo bar, hero's sr-only title, the closing section's eyebrow/copy, the footer's "Our workshop" link, the quick-view modal's spec grid, and the chat widget's canned reply) — explicit "we don't mention any three sixty thing in the website." Copy that used to name it now says "our workshop" instead. If you add new copy anywhere that would naturally reference the maker, don't name Three Sixty — say "our workshop," "handmade in India," or similar.

- **Deliverable:** `after-hours.html` — one self-contained file in the project root. This is the entire product.
- **Hard constraint:** it stays a single HTML file with inline `<style>` and `<script>`. No build step, no bundler, no framework, no external JS/CSS libraries. Do not introduce one without being explicitly asked.
- Supporting files already in place: `brand-fonts.css` (real brand type, self-hosted `@font-face`), `assets/img/` (real product photography), plus reference PDFs and raw asset folders (see section 9).

## 2. Tech Constraints

- **No framework.** Vanilla HTML/CSS/JS only, all inline in `after-hours.html`.
- **Fonts:** loaded via one line, `<link rel="stylesheet" href="brand-fonts.css">` — never re-inline `@font-face` rules or swap back to a Google Fonts CDN link. Resolved through CSS custom properties:
  - `--font-display` → `'IvyPresto Display', Georgia, 'Times New Roman', serif`
  - `--font-body` → `'HK Grotesk', system-ui, -apple-system, 'Segoe UI', sans-serif`
- **Palette** (in `:root`): `--licorice:#260B0F`, `--deep:#1C0810`, `--caramel:#BF7E45`, `--bone:#D9D2BF`, `--grey:#736C58`, `--off:#F5F2EC`, plus `--ink`, `--ink-soft`, `--line`, `--line-dark`.
- **Spacing token system** (in `:root`): `--space-xs`, `--space-sm`, `--space-md`, `--space-lg`, `--sec-pad`, `--sec-pad-lg`. This is the single source of truth for section vertical padding and grid/flex gaps across the whole page. **Any new section or component must reuse these tokens.** Writing a fresh one-off `clamp()` value for padding or gap instead of reusing a token is a regression — it re-breaks the spacing consistency pass that was done deliberately.
- **Images:** every real photo uses `<img class="ph img-cover" src="assets/img/...">`. `.img-cover` is a small utility (`width/height:100%; object-fit:cover; display:block`) added *alongside* the older `.ph` gradient-placeholder system specifically so the existing `.ph`-keyed hover/position/transform CSS (built for gradient `<div>` placeholders) keeps working unchanged on real `<img>` elements. Never strip the `.ph` class off an image just because it's "not actually a placeholder anymore" — it's load-bearing CSS wiring, not a naming leftover.
- **Responsive breakpoints in use:** 1100px, 900px, 600px (desktop → tablet → mobile), plus a `prefers-reduced-motion` block. The two viewports actually tested during this build were **390×844** and **1920×1080** — verify against those first if you change layout.

## 3. Site-Wide Layout Guideline (checkable — verify against this for any new section or product grid)

This is a standing rule, not a one-off fix. It was written after converting every product-card grid to a carousel and auditing the whole page for one-fold fit (both explicitly requested as a locked, checkable guideline going forward, not just a single visual pass).

**Rule A — every product-card grid on the page is a single-row horizontal carousel, never a wrapping grid.** Concretely:
- Structure: a `.mf-row-wrap` containing two `.car-nav.mf-nav` (`.prev`/`.next`) buttons, the scrollable row itself (`overflow-x:auto`, `data-carousel-row`), and a `.mf-scrollbar`/`.mf-scrollbar-thumb` branded progress bar (`data-carousel-thumb`). This is the **one** mechanism for every product row on the page — Shop by Texture's `.mf-row` and each category-split section's `.grp-row` (which also carries the `.mf-row` class purely for shared carousel CSS/JS; `.grp-row` itself carries no layout rules of its own anymore).
- JS: one generic `initCarousel(wrap)` function (in the `<script>` block, right after the add-to-bag delegated handler) wires up every `.mf-row-wrap` on the page — there is no per-section carousel implementation. Filter/circle-selector handlers call a shared `refilterRow(row, predicate)` helper that hides/shows cards and re-runs that row's own `update()` (recentring the `is-few` state, resetting `scrollLeft`, redrawing the scrollbar thumb).
- Sizing target: at standard desktop width, a carousel should show **exactly 4 product cards fully visible plus a partial next card cut off at the trailing edge** — a deliberate "there's more" affordance, not a bug to eliminate. Shop by Texture uses `.mf-row .product-card{flex:0 0 clamp(230px,25vw,290px)}`; the category-split sections sit in a narrower two-column banner+panel layout so `.grp-row .product-card{flex-basis:clamp(190px,22vw,230px)}` is smaller and lands nearer "~2-3 full + a peek" in the width actually available — **don't unify these two card widths thinking the difference is a bug.**
- **SUPERSEDED — don't rely on a row's available width happening to overflow by chance.** The first pass sized cards so a peek showed only at exactly 1920px — at a real laptop width (e.g. 1440px, or any monitor with browser chrome/toolbars eating into the viewport) the row could land on an exact multiple of the card width and show zero peek, or worse, undersize to 3-full-cards-then-immediately-the-arrow with no visible "there's more" cue at all. Fixed by capping `.mf-row-wrap`'s own `max-width` to a fixed multiple of the card width — `#materials-filter .mf-row-wrap{max-width:calc(4.5 * clamp(230px,25vw,290px) + 4 * var(--space-sm))}` and `.grp-content .mf-row-wrap{max-width:calc(3.5 * clamp(190px,22vw,230px) + 3 * var(--space-sm))}` — so the row deliberately never sizes itself to an exact card multiple; it either fills 100% of a narrower container (still showing whatever natural overflow that produces) or gets capped at N.5 cards' width on a wide one. *Reason: explicit "product cards at 100% zoom should be 5th card half visible, i still don't see that change" — verified by testing at 1440px, not just 1920px.* If you resize cards again, re-test the peek at 1440px and 1280px too, not just 1920px — a fix that only works at exactly one viewport width isn't a fix.
- Every texture (Shop by Texture) and every group (category-split sections) must carry **at least 5 product cards** so the peek is actually visible in practice (4 cards exactly-filling a row shows no overflow, no peek) — if you add a texture/group with only 1-4 cards, top it up with an invented preview SKU (same convention as the rest) rather than leaving it short.
- **The desktop texture tab bar (`.mf-tabs .tab`) is deliberately wide — `min-width:122px`, `padding:14px 25px`, and `.mf-head`'s own `max-width` raised to `1020px`** so the tabs have room to actually grow (was `960px`, which silently capped the bar's width regardless of how much bigger `.tab`'s own padding/min-width got — check `.mf-head`'s max-width first if a future tab-bar resize doesn't seem to do anything). Total bar width went ~670px → ~892px (≈+33%). *Reason: explicit "they still feel cluttered, let's space them out more, its overall length should increase at least by 25% in total."* Don't shrink `.mf-head`'s max-width back down without re-checking the tab bar still has room to breathe.
- **CSS Grid gotcha to remember:** `.cs-panel` (`#hosting`/`#furniture`/`#accessories`'s text/carousel column) needs `min-width:0`. Without it, a grid item's default `min-width:auto` uses the *un-scrolled* carousel content's full min-content width as a floor, which silently forces the grid column to blow out past its intended `1.15fr` share and collapses the banner column next to it. If a category-split banner ever looks squeezed/wrong-proportioned again after touching `.grp-row`, check this first before touching the grid-template-columns ratio itself.
- **SUPERSEDED — `.mf-tabs` (the texture filter bar) on mobile (`≤600px`) is a CSS Grid where "All" spans its own full-width row, then the 6 real textures fill a clean 3×2 grid below it.** First pass treated all 7 tabs as one even 3-column grid (3+3+1, the lone 7th tab centered awkwardly in the middle column of its own row). Explicitly refined: "let's have all in one row all the three cells merged, and the 6 types can be in the next two rows" — `.mf-tabs .tab:first-child{grid-column:1/-1}` makes "All" its own full-width row (it's a reset, not one of the 6 textures, so it reads better as its own row rather than sharing a row-count with them), then Croco/Split Suede/Hair On Hide/Plain/Fine-Grained/Shagreen auto-place into a proper 3-column × 2-row grid. Border logic: `:nth-child(3n+1):not(:first-child)` drops the right border on the rightmost column of the texture grid, `:nth-last-child(-n+3)` drops the bottom border on its last row. Don't go back to treating "All" as just the first of 7 equal grid cells.

**Rule B — every section on the page is checked against one full viewport fold at both 1920×1080 and 390×844 — but that check must account for real browser chrome, not just the raw viewport height.** A section measured at, say, 1017px against a 1080px *raw* viewport technically "fits," but a real browser's address bar, tab strip, and bookmarks bar can easily eat 150-250px, so anything over roughly 850-900px effectively doesn't fit on a real desktop at 100% zoom — confirmed directly ("this entire section i can see at 67% zoom in google chrome"). Trim sections to comfortably clear ~850px, not just the theoretical 1080px ceiling, and *unless* fitting it would require reversing an existing locked decision or genuinely harm legibility — in which case the exception is named explicitly here, not silently skipped:
- **Exception: `footer`.** ~658px desktop (fits), ~1162px mobile (does not, and isn't expected to) — it's a multi-column link directory (3 nav columns + brand block + bottom bar) that stacks to one column on mobile; compressing it to fit one fold would mean cutting real navigation links, which isn't in scope of a "make it editorial" size pass. Treat any future footer content addition as adding to this already-accepted exception, not a new fold violation to chase.
- Every other section (hero, `#categories`, `#materials-filter`, `.stats`, `#hosting`, `#reviews`, `#furniture`, `#accessories`, `.trust-break`, `#closing`, `#newsletter`) fits one fold at both sizes as of this pass, re-verified against the ~850px real-world ceiling (Shop by Texture came down from 1017px to ~870-940px this way). If a future change pushes one over, re-tighten it — don't treat "it doesn't fit" as acceptable by default.
- **Shop by Texture was cut a third time, by explicit percentage this round**: "reduce the shop by texture size height majorly... in mobile 10% shorten it, in desktop shorten it by 20%." Desktop went ~871px → ~707px (≈19% cut); mobile ~783px → ~714px (≈9% cut) — measured against the section's height immediately before this specific request, not the original pre-redesign height. Levers used: `.material-filter`'s own top/bottom padding, `.mf-head h2`/`.mf-sub` font-size and margins (desktop *and* mobile, not mobile-only this time), `.mf-tabs .tab` padding, `.mf-row .product-card` max-width (340px → 290px → 260px → 235px → 220px across this project's several rounds of tuning — if asked to shrink again, keep nudging this down rather than only touching padding), and `.mf-row-wrap`/`.mf-foot` margins. The carousel's `max-width` cap formula (`4.5 * clamp(...) + 4 * var(--space-sm)`, see Rule A) was updated in lockstep each time the card clamp changed — if you resize the card again, update that calc too or the 4-full-cards-plus-peek target silently drifts.
- Specific levers already used, reusable for future tightening: `.cs-panel{padding;gap}` (both desktop and the `600px` mobile override), `.cs-visual{min-height}` (note `#hosting .cs-visual` has its own more-specific rule that needs its own mobile override, not just the shared `.cs-visual` one), `#catTitle{white-space:nowrap}` + a widened `.categories .wrap` grid column for a one-line "The Shops" heading, `.tile{aspect-ratio}` (shrunk to `16/7` on mobile from `16/10`), `.material-filter`'s own top/bottom padding and `.mf-head`/`.mf-sub`/`.mf-foot` font-size and margin (trimmed a second time, desktop included, not just mobile), and `.grp-content{margin-top}` spacing at the `600px` breakpoint.

## 4. Locked Design Decisions

Each of these was a deliberate choice made after discussion, not a default. Do not silently reverse any of them.

- **Hero has zero overlay.** No headline, no tagline, no CTA button, no scrim/shade `<div>` on top of the hero video. **The hero "video" is no longer a `<video>` element — it's two animated WebP images** (`.hero-video.desktop`/`.mobile`, swapped via CSS at the 900px breakpoint), converted from the original MP4s with ffmpeg (`scale=1280:-2`/`scale=-2:960`, `fps=15`, `-q:v 50 -compression_level 6 -method 6`) and living at `assets/video/hero-desktop.webp` (5.6MB, was 32MB) / `hero-mobile.webp` (3.4MB, was 34MB). *Reason: the raw MP4s were too large to reasonably serve/commit (and were previously `.gitignore`d entirely, silently 404ing on the deployed GitHub Pages site) — explicit ask to "convert the video to a webp ... optimise it."* Since `<img>` has no `play()`/`pause()` API, reduced-motion no longer pauses the animation — instead JS swaps `src` to a static poster frame (`data-poster` attribute → `hero-desktop-poster.jpg`/`hero-mobile-poster.jpg`, first frame extracted via ffmpeg). Don't revert to `<video>`/MP4 for the hero, and don't remove the `data-poster` swap — it's the only reduced-motion affordance available for an animated-WebP hero.
- **`#materials-filter` and `#hosting` are intentionally swapped from their original build.** `id="materials-filter"` = the "Materials" browse-by-leather section (banner + 4 leather-type tabs + an overlapping product row). `id="hosting"` = the real Hosting & Bar category section. *Reason: the two sections were re-purposed mid-project; nav links and category tiles already point at the correct one via these ids — swapping them back would silently break navigation.*
- **`.category-split` is the shared component for all three category sections** (`#hosting`, `#furniture`, `#accessories`): `.cs-visual` (banner image) + `.cs-panel` (eyebrow, `h2`, one-line `.cs-sub`, then a `.sub-grid` of 1:1 `.sub-tile` subcategory tiles). Hosting and Furniture are banner-left/panel-right (DOM order = visual order). **`#accessories` is mirrored on desktop only** — `#accessories .cs-visual{order:2}` / `#accessories .cs-panel{order:1}` puts the banner on the right and tiles on the left at ≥901px; both are reset to `order:0` inside the `900px` breakpoint so mobile stacks in natural DOM order (banner, then panel). *Reason: explicit ask to reverse Accessories specifically, desktop-position-only — "mobile colour is what needs to change" (that's the `.trust-break` background, not this).* Don't extend the mirroring to Hosting or Furniture, and don't let the `order` swap leak into the mobile single-column breakpoint.
- **REMOVED — `.sub-grid`/`.cols-3`/`.cols-4` no longer exist.** Both the "flex not grid, for centering" rule and the "minimum 5 tiles per section" rule were specific to the old subcategory-tile component and don't apply to its replacement, `.cs-groups`/`.grp-row` (which uses the same flex-centering *technique* but with a fixed 4 groups per section — see the group-carousel rule above). `.grp-row` still uses `display:flex;justify-content:center` for the same reason (so a filtered 2-card group centers instead of hugging the left edge) — don't switch that back to `display:grid` either.
- **Category-split panel background alternates dark → white → dark** across Hosting & Bar → Furniture → Accessories (unchanged by the Accessories position-mirroring above — only left/right placement flipped, not the panel's own dark colour). *Reason: explicit alternation request; Hosting & Bar's color was an extrapolation to keep the three-section rhythm consistent since only Furniture/Accessories were named explicitly — flag if this should instead match one specific section.*
- **SUPERSEDED — `#hosting`, `#furniture`, and `#accessories` now show real product/SKU cards (price, wishlist, ATC, quick-view), not pure navigation tiles.** This formally reverses the earlier "subcategory tiles only, no product cards" decision (see the group-carousel rule below for the full replacement). *Reason: explicit ask, citing a jewellery-site reference ("Moments, Made Personal" birthstone/month selector driving a product grid) — "the reference's product cards have a wishlist heart and a price... yes, become real product cards."*
- **SUPERSEDED (again) — `.tile` (3 main `#categories` tiles) now DOES have a gradient overlay, matching the `.product-card` treatment.** History: (1) full-tile veil → (2) veil removed, 3-layer `text-shadow` "glow" → (3) glow replaced with a solid caption-plate → (4) plate rejected, settled on a defined-edge `text-shadow` with no background at all → (5) **explicitly reversed again**: "the category tile that we have we would need to introduce an overlay similar to how we have overlays across our product cards." `.tile::before` now carries the exact same gradient recipe as `.product-card .media::before` (`linear-gradient(0deg,rgba(28,8,16,.85) 0%,rgba(28,8,16,.38) 38%,rgba(28,8,16,.04) 62%,transparent 80%)`), and the old per-element `text-shadow` was removed from `.tile .cap h3`/`.go` since the gradient now does that legibility work. **Caption position also changed**: `.tile .cap` moved from anchored bottom-left (`left/right:22px;bottom:22px`, left-aligned text) to bottom-right (`left/right:26px;bottom:26px;text-align:right`), and `.go` ("Shop the range") is now underlined (`text-decoration:underline`) instead of relying on a hover-only opacity change alone. *Reason: explicit "the text inside category tiles we would need to move it towards more bottom right... underline shop the range."* Don't revert to the no-overlay/bottom-left/no-underline version — this was a deliberate, explicit design reversal, not a regression to catch.
- **REMOVED — `.sub-tile`/`.sub-grid` (the portrait-photo-+-caption subcategory tiles) no longer exist anywhere on the page.** They went through two full redesigns (on-image label + arrow badge → portrait photo + plain caption below) before being replaced entirely by the `.cs-groups` circular group-carousel described next. Don't resurrect `.sub-tile`/`.sub-grid` markup or CSS from an old commit — the whole navigation-tile concept for these three sections is gone, not just restyled.
